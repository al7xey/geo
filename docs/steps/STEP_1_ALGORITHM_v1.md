# ШАГ 1
## Чтение сайта и технические проверки

**GEO-аудит · Подробный алгоритм · Редакция 1.0 · 31.10.2026**

Документ определяет ограниченный сбор страниц, техническую диагностику и подготовку проверяемого материала для профиля компании на шаге 2. Он учитывает исправления исходного алгоритма и использует результат шага 0. Численные пороги являются настройками первой версии, а не доказанными нормативами GEO.

### 1.0. Цель и границы

Собрать полезные тексты и метаданные сайта, установить наблюдаемые ограничения доступа и сохранить основания каждой проверки. На выходе должно быть понятно, какие страницы прочитаны, что помешало остальным и на каком материале можно строить профиль.

Исполнитель: Python, HTTPX, trafilatura, BeautifulSoup, protego или проверенный совместимый парсер; безопасный XML-разбор. Playwright подключается только как необязательная ограниченная диагностика. Модели и платный поиск на этом шаге не используются.

### Основные исправления

| Было в исходной версии | Уточнённое решение |
|---|---|
| Не менее трёх страниц по 300 символов | Ориентир покрытия; полезный одностраничник тоже допускается |
| Доступ 14 роботов | Документируемый реестр без искусственного фиксированного количества |
| Сайт одинаков для браузера и роботов | Ограниченные наблюдения по User-Agent без обещания реального доступа робота |
| Малый текст означает проблему JS | Сравнение исходного и rendered-текста с сохранением неопределённости |
| Проверка прошла / не прошла | pass, fail, warning, unknown, not_applicable с основаниями |
| До 30 страниц без детализации охвата | Учёт кандидатов, причин отбора, дубликатов, сбоев и остановки по лимиту |

### Общий порядок

Проверить вход шага 0 → получить robots → обнаружить URL → выбрать и прочитать страницы → извлечь текст → проверить директивы и транспорт → выполнить разрешённые дополнительные диагностики → оценить достаточность → сохранить результаты и передать материал шагу 2.

Выходы: crawl.json, checks.json, run.json и raw-манифест. Успех извлечения текста не означает успех всех технических проверок. Ошибка отдельной страницы не должна уничтожать данные остальных.

# 1. Вход, состояние запуска и подготовка

### 1.1. Что поступает из шага 0

| Объект | Проверка перед продолжением |
|---|---|
| site.json | Известная schema_version, run_id и can_enter_step1=true |
| Выбранный HTML | Файл существует, хэш соответствует selected_evidence_id |
| effective_url и origin | Совпадают с наблюдаемым конечным ответом |
| allowed_hosts и path_scope | Не расширены произвольно после проверки адреса |
| Budget | Учтены запросы и время шага 0, общий deadline ещё не истёк |
| Конфигурация | Версия сохранена; есть лимиты, язык запроса и собственный User-Agent |

Если вход не согласован, вернуть INPUT_ARTIFACT_INVALID. Не подставлять пустые тексты и не выдавать повреждённый результат шага 0 за успешный вход. Сохранённый входной ответ повторно не загружается только ради начала шага 1.

### 1.2. Инициализация

Создать очередь URL, реестр origin, хранилище ответов, карту нормализованных URL и redirect-алиасов, реестр доказательств, список проверок и счётчики. Параметры сети общие со шагом 0: фактическая проверка публичного назначения, TLS verification, ручные редиректы и ограниченные повторы.

У скрипта собственный честный User-Agent GEOAudit/0.1. Название не меняется в ответ на Disallow. Дополнительные запросы с другим User-Agent относятся только к явно включённой диагностике и не подменяют основной обход.

### 1.3. Разрешение чтения и сохранённая входная страница

Шаг 0 является проверкой явно введённого адреса. До автоматического чтения остальных страниц шаг 1 проверяет правила для своего обходчика. Если robots запрещает этот обход, новые страницы не запрашиваются. Уже полученный входной HTML можно сохранить и описать как ограниченное входное наблюдение; он не доказывает разрешение последующего обхода.

Поле crawl_permission имеет значения allowed, disallowed или unknown и область origin/URL. Оно отличается от can_enter_step1. Даже при disallowed/unknown сохраняются robots-наблюдения, результаты шага 0 и причина ограничения.

### 1.4. Условия остановки

Общий deadline, бюджет запросов, неподтверждённый внешний хост, сетевой запрет или ошибка обязательного хранения заканчивают соответствующую ветвь. Алгоритм фиксирует partial/needs_input/failed по общему правилу и сохраняет всё, что уже получено. Никакого бесконечного ожидания браузера, ответа пользователя или Retry-After.

# 2. Получение robots.txt

### 2.1. Отдельный документ для каждого origin

URL строится как origin + /robots.txt. Для http://example.com/ru/ это http://example.com/robots.txt. Разные схема, хост и порт требуют отдельных результатов. Перенос правил между HTTP и HTTPS без наблюдения недопустим. [S1, S2]

Применяется потоковый GET через общий клиент. Сохраняются исходное тело, код, заголовки, время, request_id, хэш и origin, для которого получены правила. Кэш допускается внутри запуска; между запусками нужен возраст и HTTP-валидация. Для первой реализации достаточно кэша только на время запуска.

### 2.2. Таблица решения для нашего обходчика

| Полученный результат | Состояние и политика проекта |
|---|---|
| 200, корректный текст правил | present; применить разобранные правила |
| 200, пустой корректный файл / 204 | empty; явных ограничений нет; HTTP-особенность сохранить |
| 404/410 | absent; явного robots-запрета нет |
| 401/403 | access_denied; unknown, дальнейший автоматический обход приостановить |
| 429 | Временное ограничение; учитывать Retry-After; по исчерпании бюджета unknown |
| 5xx или сетевая ошибка | После ограниченного повтора unreachable; unknown и пауза обхода |
| HTML challenge вместо текста | invalid_response; не объявлять файл отсутствующим |
| Неполное тело, 206, превышение лимита | incomplete; не делать окончательный вывод «всё разрешено» |

Консервативная остановка на 401/403 является политикой нашего продукта. Её нельзя выдавать за универсальное поведение всех поисковых систем. Техническая неизвестность также не равна директиве владельца Disallow: /. [S1, S2]

### 2.3. Редиректы файла

До пяти безопасных переходов robots.txt могут вести между публичными хостами. Это отдельное правило получения служебного ресурса. Проверять каждое назначение и не расширять allowed_hosts для HTML-обхода. Правила относятся к первоначальному origin, а конечный URL файла хранится отдельно. При запрещённом назначении или незавершённой цепочке результат unknown. [S1]

### 2.4. Размер и ошибки формата

Лимит разбора - 512 KiB. При превышении хранить доступную часть и флаг усечения; собственный обход приостановить, потому что окончательные правила неизвестны. При отдельных ошибках строк использовать корректно разобранную часть и сохранить предупреждения. HTML с несколькими случайными словами Allow нельзя автоматически считать достоверным robots.txt.

Каждое ограничение должно иметь точную причину: ROBOTS_FORBIDS, ROBOTS_UNREACHABLE, ROBOTS_ACCESS_DENIED, ROBOTS_TRUNCATED или ROBOTS_INVALID_RESPONSE. Только первое означает установленный запрет из правил.

# 3. Оценка правил robots по URL

### 3.1. Парсер и объяснимость

Использовать protego либо другой парсер с проверенной семантикой. Зафиксировать версию и набор совместимости. Регулярное выражение «есть ли Disallow» не заменяет разбор групп, путей и приоритетов. Хранить исходные строки до нормализации. [S3]

Для каждого выбранного URL оценить собственного обходчика и токены из реестра. Результат относится к точному URL и origin. Если для главной разрешено, а /services/ запрещено, отчёт должен показать оба наблюдения, а не «робот имеет доступ ко всему сайту».

### 3.2. Что сохранять в robots_decision

| Поле | Значение |
|---|---|
| robots_evidence_id | Исходник с номерами строк |
| evaluated_url, origin | Адрес и область проверки |
| product_token | Точный токен из реестра |
| decision | allowed, disallowed или unknown |
| matched_group_lines | Группа, применённая парсером |
| decisive_rule_lines | Правило, определившее результат; может быть пустым |
| reason | Разрешение, запрет, отсутствие подходящего ограничения или невозможность оценки |
| parser_version | Версия и политика совместимости |

При отсутствии ограничения номера решающих правил могут быть пустыми. Нельзя придумывать строку «Allow», которой нет в файле. Если парсер не выдаёт объяснение, слой сопоставления обязан подтверждать решение теми же правилами. При расхождении объяснения с парсером проверка получает unknown, а не фиктивную ссылку на строку.

### 3.3. Контрольные случаи

Проверить: регистр токена, специфическую группу и wildcard-группу, несколько подходящих групп, пустой Disallow, пересекающиеся Allow/Disallow, wildcard, конец шаблона, percent-encoded путь и query. Условные примеры должны проходить и прямую проверку парсера, и проверку доказательств. Особенности совместимости с конкретным провайдером отмечать отдельно. [S1, S2, S3]

### 3.4. Crawl-delay и частота

Если для собственного токена есть поддерживаемый Crawl-delay, использовать более строгий интервал между ним и нашим минимальным интервалом. Неподдерживаемое расширение фиксируется как raw-директива. Не приписывать всем провайдерам одинаковую поддержку нестандартных правил.

Для URL, запрещённого собственному обходчику, сохраняется запись skipped_robots и доказательство. Текст такой страницы не считается прочитанным. Наличие URL в sitemap или внутренних ссылках не отменяет Disallow.

# 4. Реестр роботов и смысл проверок

### 4.1. Структура записи реестра

robot_id, operator, product_token, purpose, robots_applicability, http_user_agent либо null, documentation_url, verified_at, registry_version и interpretation_notes. HTTP-строки брать из официальной документации с датой проверки; не составлять несуществующие агенты по названию продукта.

Начальный реестр содержит восемь токенов. Число 14 не является обязательным критерием качества. Дополнительные роботы включаются, когда документированы их роль и правила интерпретации.

| Токен | Назначение / ограничение интерпретации |
|---|---|
| OAI-SearchBot | Поисковая видимость в функциях поиска ChatGPT [S4] |
| GPTBot | Возможное использование материалов для обучения; отдельная настройка [S4] |
| ChatGPT-User | Загрузки по действию пользователя; robots может не применяться [S4] |
| Claude-SearchBot | Поисковый обход для функций Claude [S5] |
| ClaudeBot | Обход, связанный с обучением моделей [S5] |
| Claude-User | Загрузки по пользовательскому запросу [S5] |
| Googlebot | Индексирование и связанные поисковые продукты [S6] |
| Google-Extended | Управление использованием контента; собственного HTTP UA нет [S6] |

### 4.2. Что нельзя объединять

Запрет обучающему роботу не равен установленному запрету поискового продукта. Google-Extended не влияет на включение в Google Search и не должен использоваться как имя HTTP-запроса. У ChatGPT-User механически найденный Disallow сохраняется, но его применимость объясняется особенностями пользовательских загрузок. [S4, S6]

Для каждого токена различать robots_policy и observed_http_response. Первое вычисляется из файла, второе возможно только в отдельной диагностике. Если HTTP User-Agent отсутствует, probe получает not_applicable. Если документация устарела или неоднозначна, registry_entry_state=needs_verification, интерпретация ограничена.

### 4.3. Формат вывода

Корректно: «В robots.txt для OAI-SearchBot путь /services/ запрещён правилом на строке 12». Некорректно: «Вас нет в ChatGPT, потому что закрыт GPTBot». Алгоритм наблюдает техническое условие, но не устанавливает единственную причину наличия или отсутствия бренда в ответах.

Обновление реестра версионируется отдельно от алгоритма. Старый запуск сохраняет применявшийся реестр. Перед разработкой реальные UA-строки и особенности операторов проверяются по источникам, а не копируются из неофициального списка.

# 5. Sitemap и обнаружение URL

### 5.1. Источники кандидатов

Начать с входной страницы и её ссылок. Добавить Sitemap-директивы из корректно полученного robots.txt. Если их нет или они не дали результата, ограниченно проверить /sitemap.xml и /sitemap_index.xml. Не перебирать десятки предполагаемых названий.

Сохранять provenance: URL найден во входном HTML, в конкретном sitemap либо на другой прочитанной странице. При нескольких источниках сохраняется список, а не перезаписывается первое основание.

### 5.2. Разбор sitemap

Поддержать XML urlset и sitemapindex с namespaces, чтение loc и gzip. Внешние сущности и сетевые обращения XML-парсера запрещены. Не делать полное дерево в памяти для произвольно большого файла. lastmod, priority и changefreq сохранять как сведения издателя, без обещания их точности. [S7]

Начальные пределы: пять различных sitemap-файлов, включая индекс; до 5 MiB после распаковки на файл; до 5000 URL суммарно; глубина ссылок на sitemap до 3 в рамках пяти файлов. Повторно встретившийся sitemap не читается снова. Все попытки, в том числе стандартные пути с 404, входят в общий HTTP-бюджет.

### 5.3. Область

URL страниц вне разрешённых хостов/префиксов не запрашивать. Наличие ссылки в sitemap не расширяет область анализа. Sitemap на внешнем CDN по умолчанию получает skipped_external_resource; загрузка допустима только при отдельно настроенном allowed_sitemap_hosts, с общей проверкой публичного назначения. Разрешение служебного файла не разрешает HTML-обход этого CDN.

Относительные loc или другой нестандартный формат сохранить как проблему. При допустимом восстановлении адреса отметить inferred_url; не выдавать восстановленное значение за исходный корректный loc. В первой реализации безопаснее пропустить некорректную запись, сохранив причину.

### 5.4. Отсутствие sitemap

404, пустой, невалидный или недоступный sitemap не останавливает чтение внутренних ссылок. Проверка фиксирует ограничение обнаружения URL. Формулировка «страницы не индексируются» из отсутствия карты недопустима: карта является средством обнаружения, а не доказательством индексирования.

Если индекс больше выделенного лимита, сохранить число разобранных и пропущенных файлов, stop_reason и порядок выбора. Вывод «на сайте только столько страниц» делать нельзя. В coverage записать sitemap_truncated=true и реальное ограничение этой выборки.

# 6. Очередь, приоритеты и границы обхода

### 6.1. Детерминированный выбор

Кандидат имеет URL, источники обнаружения, предполагаемую роль, язык, приоритет и порядковый номер. Очередь сортируется по роли и устойчивому tie-breaker, чтобы одинаковый вход давал объяснимый выбор. Роль - эвристика по URL, анкору и окружению ссылки; она сохраняется с основанием.

| Приоритет | Категория |
|---|---|
| 0 | Входная страница; главная при наличии допустимой ссылки |
| 1 | О компании, описание бизнеса |
| 2 | Основные услуги и продукты |
| 3 | Цены, тарифы и коммерческие условия |
| 4 | Контакты, география, филиалы |
| 5 | FAQ и полезные ответы |
| 6 | Остальные содержательные разделы в доступном бюджете |

### 6.2. Лимиты очереди и дубликаты

Не более 30 выбранных HTML-кандидатов, включая входной. Неудачная загрузка расходует слот: алгоритм не заменяет каждую ошибку бесконечными новыми страницами. HTTP-повтор расходует запрос, но не создаёт новый кандидат. Наблюдаемые redirect-алиасы и точные дубликаты не считаются новыми прочитанными страницами.

Хранить максимум 5000 нормализованных кандидатов очереди. Для первой версии разрешить не более двух вариантов query на одном пути. При превышении сохранить skipped_parameter_limit. Не удалять все query: они могут задавать язык или регион. Fragment удаляется, порядок значимых параметров для сетевого запроса сохраняется.

### 6.3. Исключения

Не отправлять формы; не заходить в logout, корзину, личный кабинет, внутренний поиск, бесконечные календари и генераторы фильтров. Правила исключения являются конфигурацией и записываются как skip_reason. Обычный информационный адрес нельзя исключать только по случайному совпадению короткой подстроки.

Для нового origin из уже разрешённого хоста сначала получить его robots. На каждом redirect проверить область, назначение и бюджет. Неизвестный внешний хост фиксируется в pending_external_urls; его обнаружение не прерывает все остальные разрешённые ветви.

### 6.4. Показатели охвата

Раздельно считать discovered_urls, selected_candidates, fetch_successes, unique_html_pages, extracted_pages, useful_pages, skipped и failed. Причины пропуска не смешивать с сетевыми ошибками. По завершении хранить URL-списки или проверяемые ссылки на них. Canonical и одинаковый хэш - сигналы дублирования; при сомнении страницы сохраняются раздельно с duplicate_candidate, без необоснованного слияния.

# 7. HTML, основной текст и происхождение

### 7.1. Сохранение до преобразования

Для каждой успешной загрузки сохранить исходное тело и метаданные через общий evidence-store. Различать content-encoded body, распакованный HTML, декодированную строку и rendered DOM. Исходник не заменять «очищенной» версией. На каждом представлении фиксировать SHA-256, размер, source_evidence_id и transform_version.

В raw-манифесте хранить requested_url, effective_url, время, HTTP-статус, заголовки из разрешённого набора, charset, полноту получения и цепочку редиректов. Различные заголовки с одинаковым именем сохранять списком. Set-Cookie не включать в публичный журнал.

### 7.2. Извлечение

1. Применить trafilatura к декодированному HTML с сохранением значимых списков и таблиц.
2. Оценить извлечение: пусто ли оно, не состоит ли только из навигации/согласия с cookies, не потеряны ли очевидные содержательные блоки.
3. При непригодном результате выполнить fallback через BeautifulSoup: удалить script/style и явные служебные блоки, выделить main/article либо доступную содержательную область.
4. Сохранить оба кандидата, если они существенно различаются, и объяснить выбор. Не склеивать автоматически дублирующийся текст двух экстракторов.
5. Применить фиксированную нормализацию пробелов и переносов, затем вычислить длину и хэш текста. Сохранить исходное извлечение отдельно, если нормализация меняет адресацию фрагментов.

### 7.3. Структурированный результат страницы

| Группа | Поля |
|---|---|
| Идентификация | page_id, URL, origin, fetch_id, evidence_id |
| Содержимое | title, h1/h2, main_text, текст таблиц/списков |
| Извлечение | method, extractor_version, text_chars, text_hash |
| Метаданные | lang, hreflang, canonical, robots directives |
| Качество | content_state, useful_candidate, ограничения и причины |
| Связи | source_evidence_id, derived_evidence_id, обнаружившие страницы |

Число символов считается после заданной нормализации Unicode-пробелов; правило версии фиксируется. Текст заголовков/таблиц, уже включённый в main_text, не прибавляется повторно для оценки достаточности.

### 7.4. Подготовка цитат для шага 2

У будущего факта должны быть page_id, evidence_id, точный фрагмент текста и его позиция в сохранённом представлении. offsets относятся к конкретному text_hash и не обещают совпадение с байтами HTML. Тексты сайта передаются будущей модели как недоверенные данные, отделённые от инструкций; содержащиеся в них команды не становятся заданиями проекта.

# 8. Индексирование и ограничения фрагментов

### 8.1. Какие данные читать

Из HTTP-ответа - все X-Robots-Tag, включая повторяющиеся. Из HTML - meta name=robots, meta с конкретным именем робота, canonical, lang/hreflang и области data-nosnippet. Сохранять исходную запись, адресата, нормализованные токены и доказательство. rendered-директивы, если получены, хранить отдельно от исходных. [S8]

### 8.2. Разные вопросы - разные проверки

| Проверка | Что устанавливается |
|---|---|
| robots_policy | Может ли заданный обходчик читать этот URL по файлу правил |
| indexing_directives | Какие явные инструкции индексирования опубликованы |
| snippet_directives | Какие ограничения фрагментов/использования текста обнаружены |
| canonical_signal | Какой канонический адрес заявлен страницей |
| observed_access | Как ответил сервер на конкретный запрос из нашей среды |

noindex и none обрабатываются как явные директивы, с сохранением адресата. nosnippet, max-snippet и data-nosnippet не превращаются в общий «запрет ИИ»: смысл зависит от поддерживающего продукта. Применимость к Google объясняется по его документации; перенос на других операторов требует их источника. [S8]

### 8.3. Конфликты и неполнота

Если обнаружены несколько общих и адресованных директив, сохранить весь набор. Интерпретировать совместно только по документированной политике оператора; при неизвестном результате дать unknown с исходными значениями. Не выбирать удобную строку и не удалять конфликт.

Если страница не загружена из-за robots или доступа, её meta-правила не наблюдались. Отсутствие наблюдения нельзя превратить в «noindex не найден, проверка пройдена». Записать unknown и причину. При успешном полном чтении допустима формулировка «явный noindex в полученном HTML и заголовках не обнаружен», с указанием границ проверки.

### 8.4. Приоритет проблем

Директива на странице услуги и директива на служебной странице - разные по охвату наблюдения. В checks сохранять роль страницы, число затронутых прочитанных URL и доказательства. План действий на более позднем шаге сможет расставить приоритеты, не выдумывая покрытие всего сайта.

Отсутствие запретов не доказывает индексирование, цитирование или присутствие компании в нейроответах. Canonical на внешний хост фиксируется как сигнал; переход по нему не выполняется автоматически и область чтения не расширяется.

# 8.5. HTTPS и различия версий сайта

### Повторное использование шага 0

Вначале прочитать TLS-наблюдения и redirect-цепочки шага 0. Исправный выбранный HTTPS даёт подтверждённое наблюдение для этого соединения; TLS certificate failure остаётся fail, даже если HTML удалось получить по HTTP. Не отправлять повторный запрос только ради переноса этих данных в checks.json.

Если пользователь ввёл HTTP и HTTPS ещё не проверялся, подготовить альтернативный HTTPS URL с тем же хостом, путём и query. Выполнить один ограниченный диагностический GET через общий клиент, без отключения TLS и расширения области. Допустимые временные повторы расходуют обычный бюджет. Проверка не запускает новый рекурсивный обход.

| Наблюдение | Технический вывод |
|---|---|
| HTTPS соединение и сертификат проверены | https_transport=pass для наблюдаемого URL |
| Ошибка проверки сертификата | https_transport=fail с отдельным кодом причины |
| Отказ/таймаут/DNS-сбой | unknown либо warning по природе наблюдения; не «HTTPS отсутствует» |
| HTTPS вернул 403 | TLS мог быть исправен; access и TLS оцениваются отдельно |
| HTTPS перенаправил на HTTP | warning: наблюдён downgrade; конечный HTML не становится HTTPS-страницей |
| Обе схемы дали разные страницы | Зафиксировать различие; не смешивать тексты и директивы |

### Выбор текста и origin

Основной входной материал остаётся связан с выбранным URL шага 0. Исправная альтернативная HTTPS-версия может стать кандидатом отдельного явно зафиксированного перехода, но не незаметной заменой уже собранного корпуса. Если пользователь предпочитает анализ HTTPS-варианта, обычный повторный запуск с этим URL даст однозначную новую выборку.

Robots для HTTP не переносится на HTTPS. Проверка доступности одной альтернативной страницы является диагностическим наблюдением; дальнейшее автоматическое чтение нового origin требует его собственных правил. Заголовки, canonical и тексты разных ответов сохраняются с разными evidence_id.

### Ограничение интерпретации

Проверяется защищённость и доступность конкретного соединения из среды аудита. Этот этап не является полным аудитом TLS-конфигурации, всех сертификатных цепочек и всех узлов CDN. Если данных шага 0 достаточно, это явно отражается как reused_evidence; если бюджет закончился до проверки - unknown с причиной.

# 9. Диагностика JavaScript

### 9.1. Когда включать

Кандидаты: очень мало основного текста при наличии оболочки приложения, явный placeholder загрузки или существенное расхождение экстракторов. Само наличие script не является основанием. Выбрать максимум пять страниц с наибольшей диагностической ценностью и сохранить selection_reason.

Playwright необязателен. Если пакет, Chromium или безопасная среда недоступны, записать unknown с конкретной причиной. Отказ браузерной ветви не ломает статический обход. Если robots запрещает собственный доступ или есть подтверждённая CAPTCHA/авторизация, рендеринг не применяется для обхода.

### 9.2. Контролируемый запуск

Изолированный browser context без личного профиля, cookies и автоматической авторизации. Язык и базовые условия запроса согласованы со статической попыткой; различия записываются. TLS verification включена. Downloads, popups и service workers заблокированы; фоновые эффекты и методы запросов ограничены.

Для первой версии разрешены только GET/HEAD браузерных ресурсов. Если приложение требует POST, этот ресурс блокируется и ограничение сохраняется: низкий результат такого рендеринга нельзя выдавать за доказанную непригодность сайта. Общие таймауты, размеры и число подзапросов обязательны. [S9]

### 9.3. Условия сети

Нужен контроль фактических соединений ко всем origin, включая iframe, fetch/XHR, внешние ресурсы и попытки перехода. URL-фильтр сам по себе не защищает от DNS rebinding. При отсутствии проверенного egress-контроля браузер по умолчанию выключен и JS-проверка unknown. Публичные CDN допустимы как ограниченные ресурсы, но не становятся страницами обхода.

### 9.4. Сравнение результатов

Сохранить DOM, извлечь текст тем же правилом, что для статического HTML, затем сравнить объём и содержательность. Начальная эвристика: увеличение на 500+ символов и минимум вдвое при исходном тексте менее 1000 символов даёт флаг rendered_text_gain. При нулевой исходной длине использовать абсолютный порог. Эти числа настраиваются и версионируются.

Возможные результаты: observed_gain, no_material_gain, inconclusive. При превышении времени или бюджета результат inconclusive, а не «JS не работает». Даже observed_gain не доказывает, что текст недоступен всем роботам: браузер, время, cookies, регион и экстрактор также могут влиять на наблюдение.

На страницу - до 20 секунд. Ожидание завершения не зависит от бесконечного networkidle: использовать ограниченную загрузку и наблюдение стабилизации текста в пределах deadline. Всего до пяти страниц и 200 браузерных HTTP(S)-попыток на запуск.

# 10. User-Agent, язык и география

### 10.1. Сравнительные запросы

По умолчанию UA probes выключены. Основная проверка доступности токенов делается по robots. При включении выбрать до трёх страниц и до трёх документированных HTTP User-Agent. Не использовать токены без реального UA, в частности Google-Extended.

Сравнение выполняется при одинаковых Accept-Language и основных заголовках. Базовый ответ может переиспользоваться только при совпадении условий и достаточной близости времени. Новые запросы идут через общий клиент и расходуют его бюджет; запреты собственного обходчика и применимые ограничения проверяются заранее.

Сравнить код, конечный URL, тип, challenge-признаки и нормализованный основной текст. Точная разница хэшей не является достаточным основанием для блокировки: на странице могут меняться дата, баннер и персонализированный блок. Сохранить observation и ограничения.

Формулировка: «Из среды аудита с UA X получен 403, с базовым UA - HTML 200». Этот тест не доказывает поведение реального поискового робота с другим IP, TLS-профилем и инфраструктурой. При robots-запрете не выполнять пробу ради обхода; сохранить skipped_policy.

### 10.2. Языковые сигналы

Извлечь lang/hreflang и языковые признаки содержимого. Библиотечное определение языка допускается для достаточно длинного текста с сохранением метода; для короткой строки - unknown. Разные страницы могут быть на разных языках. Не сводить сайт к одному языку только по первой странице.

### 10.3. Географические сигналы

| Понятие | Как хранить |
|---|---|
| Страна/адрес компании | Наблюдаемый адрес, цитата, page_id; возможны несколько |
| География услуг | Явные упоминания регионов и цитаты |
| Доменная зона | Слабый признак, отдельно от установленных адресов |
| Телефонный код | Признак контакта; не гарантия местонахождения |
| Рынок будущего измерения | Отдельная настройка пользователя, а не результат выбора TLD |

В этой версии достаточно структурированных сигналов; извлекать окончательную бизнес-географию будет профиль на следующем шаге. Противоречия сохраняются. Если данных нет, values=[] и state=unknown. Не подставлять страну выполнения скрипта как страну компании.

Смешанный сайт с московским и казахстанским адресами не обязан давать единственную страну. Будущему шагу передаются обе цитаты и происхождение; пользователь сможет определить нужный рынок без потери исходных наблюдений.

# 11. Бюджеты, повторы и частичная остановка

### 11.1. Начальные пределы всего прохода 0–1

| Ресурс | Лимит |
|---|---|
| Общее время | 300 секунд, включая шаг 0 и браузер |
| HTTP-попытки без браузера | 150, включая шаг 0, redirects, retries, robots, sitemap, probes |
| Выбранные HTML-кандидаты | 30, включая входной |
| Конкурентность / интервал на хост | До 2 активных; начало не чаще раза в секунду |
| Повторы временной ошибки | До 2 дополнительно; не сверх общего бюджета |
| Redirect hops | До 5 на цепочку |
| HTML / robots | 5 MiB / 512 KiB после распаковки |
| Sitemap | 5 файлов × 5 MiB; до 5000 URL; глубина 3 |
| Очередь URL | До 5000; до 2 query-вариантов на путь |
| Browser | До 5 страниц × 20 секунд; до 200 запросов суммарно |
| UA probes | До 3 страниц × 3 агента; выключены по умолчанию |

### 11.2. Общий планировщик

Лимит проверяется перед каждой попыткой, а счётчик резервируется атомарно до отправки. Один HTTP redirect с последующим GET расходует две попытки. Повтор тоже расходует попытку. Решение из кэша увеличивает cache_hit, но не requests_sent. Браузерные попытки считаются отдельно; общая длительность едина.

Между хостами допускается ограниченная параллельность, но глобальный предел и приоритет очереди сохраняются. Не запускать все 30 страниц одновременно. Ошибки одной задачи собираются в результат; остальные ограниченные ветви могут завершиться.

### 11.3. Повторы и ожидание

Политика временных ошибок общая со шагом 0. Retry-After не игнорируется ради попадания в пяти минутный предел: если ждать дольше остатка, записать RETRY_DEFERRED и закончить ветвь. Ошибки сертификата, постоянные 4xx, robots-запрет и подтверждённый challenge не повторяются автоматически с другой личностью.

### 11.4. Завершение

При дедлайне отменить незавершённые операции, закрыть потоки/браузер и атомарно сохранить уже готовые результаты. Отмена не должна удалять raw завершённых запросов. В run.json записать stop_reason, незавершённые URL и spent/remaining counters. Если дедлайн исчерпан до всех дополнительных проверок, они получают unknown с BUDGET_EXHAUSTED.

Пользовательский partial-результат должен объяснять охват: «Прочитано 18 страниц; лимит времени остановил остальные проверки». Формулировка «весь сайт проверен» недопустима. Для повторного запуска создаётся новая версия наблюдений; silent append без согласования run_id запрещён, чтобы не удвоить счётчики.

# 12. Достаточность материала и переход

### 12.1. Что считается полезной страницей

Успешно полученный содержательный HTML, из которого извлечено не менее 300 нормализованных символов основного текста, без подтверждённого challenge, входа, soft-404 или преобладающего служебного содержимого. Релевантность бизнесу является отдельным признаком; юридический текст из 5000 символов не гарантирует материал для профиля.

Порог 300 - начальная эвристика. Не обрезать полезную короткую контактную страницу: она сохраняется как supporting_page, хотя не повышает useful_pages. Объём текста разных представлений одного URL не суммируется.

| Наблюдение | material_state | Переход |
|---|---|---|
| 3+ полезные страницы с бизнес-материалом | usable | Шаг 2 возможен; охват всё равно ограничен |
| 1–2 полезные страницы | limited | Шаг 2 возможен с отметкой ограниченного покрытия |
| Текст есть, но нет подтверждённого описания бизнеса | insufficient | Попросить описание, сохранить тексты |
| Нет полезного материала | needs_description | Шаг 2 не запускать автоматически |
| Пользователь добавил пригодное описание | user_supported | Шаг 2 возможен с явным происхождением |

Число страниц не является доказательством полноты профиля. Итоговое can_start_step2 выводится из доступного материала и известных ограничений, а не из одного количества страниц.

### 12.2. Пользовательское описание

Принимать через аргумент/файл или будущий интерфейс, без input() внутри библиотеки. Сохранить author_type=user, время, текст и source_type=user_provided. Не придумывать page_id или цитату с сайта для такого факта. Короткое пустое/бессодержательное описание вернуть на уточнение с причиной, а не выдавать за достаточный профиль.

Описание не исправляет robots, TLS, sitemap или индексирование. Например, material_state=user_supported допускает профиль, а crawl_permission=unknown и проверка HTTPS=fail остаются в технических результатах.

### 12.3. Общий статус шага

ok - основной ограниченный проход завершён и материал пригоден; это не означает отсутствие найденных проблем. partial - полезная часть получена, но есть сбои, лимиты или непроведённые включённые проверки. needs_input - нужен адрес/хост/описание. failed - нет достоверного результата или нарушено обязательное хранение.

Опциональная выключенная проверка имеет not_applicable с CONFIG_DISABLED и сама по себе не делает весь запуск partial. Если она включена, но технически не выполнена, это unknown и ограничение запуска. Отдельно сохранить status каждой проверки: обнаруженный noindex может дать fail проверке, но не технический failed всему выполнению.

# 13. Контракты crawl.json и checks.json

### 13.1. Общие поля

Все артефакты содержат schema_version, algorithm_version, run_id, config_hash, registry_version, started_at/finished_at и ссылки на доказательства. Время хранится в UTC, зона отображения отдельно. Файлы записываются атомарно после сохранения необходимых исходников.

### 13.2. Минимальный page-объект

```json
{
  "page_id": "page-003",
  "url": "https://example.com/services/",
  "fetch_state": "success",
  "evidence_id": "ev-html-003",
  "text_evidence_id": "ev-text-003",
  "title": "Услуги",
  "extraction_method": "trafilatura",
  "text_chars": 1450,
  "useful_candidate": true,
  "business_relevance": "observed",
  "discovered_from": ["page-001"],
  "selection_reason": "services_priority"
}
```

В crawl.json также находятся main_text или ссылка на его текстовый артефакт, заголовки, ссылки, исходные директивы, роли, сведения о sitemap, языковые/географические сигналы, coverage и material_state. Режим встраивания текста должен быть одинаково определён схемой, а не меняться от страницы к странице произвольно.

### 13.3. Минимальный check-объект

```json
{
  "check_id": "robots-policy-003",
  "kind": "robots_policy",
  "url": "https://example.com/services/",
  "robot_id": "oai-searchbot",
  "status": "fail",
  "observation": "disallowed",
  "evidence_ids": ["ev-robots-001"],
  "decisive_rule_lines": [12],
  "reason_code": "ROBOTS_FORBIDS",
  "limitation": "Не измеряет факт показа бренда в ответах"
}
```

Примеры учебные. Полная проверка содержит observed_at, версию правила и её область. Слово fail означает обнаруженное проверяемое препятствие в этой области. unknown означает невозможность установить результат; warning - наблюдаемое ограничение или подозрение, не равное доказанному запрету.

При валидации проверить уникальность page_id/check_id, существование каждого evidence_id и отсутствие ссылок на страницу другого запуска. Хэш текста связан с версией нормализации. Числа coverage пересчитываются из page-состояний, а не вводятся вручную.

# 14. Оркестрация, хранение и передача

### 14.1. Последовательность функций

1. load_step0_result() - проверить вход и сохранить контекст исходной проверки.
2. fetch_and_evaluate_robots() - определить собственную политику для origin и подготовить диагностику токенов.
3. discover_urls() - ссылки и разрешённые sitemap в заданных лимитах.
4. select_and_fetch_pages() - очередь, robots для каждого URL, общий бюджет и запись результатов.
5. extract_page_material() - текст, структура, происхождение и качество.
6. evaluate_directives_and_https() - технические проверки с переиспользованием шага 0; недостающая HTTPS-проверка для явного HTTP отдельно.
7. run_optional_diagnostics() - включённые UA probes и безопасный browser в остатке бюджета.
8. summarize_material_and_coverage() - пригодность, охват и условия следующего этапа.
9. validate_and_persist() - raw-манифест, crawl/checks/run, самопроверка и понятное завершение.

### 14.2. Псевдокод

```text
site, evidence, budget = verify_step0_input()
robots = load_robots(site.origin, budget)
record_robot_checks(robots, site.effective_url)
queue = discover_from_saved_entry(site, evidence)
if own_crawl_allowed(robots):
    queue += discover_from_sitemaps(robots, budget)
    for candidate in bounded_priority_queue(queue):
        page = fetch_or_skip(candidate, robots, budget)
        preserve_and_extract(page)
        add_internal_links_with_limits(page, queue)
evaluate_static_checks()
run_enabled_diagnostics_with_remaining_budget()
material = assess_material(pages, user_description)
persist_partial_or_complete_result(material)
```

### 14.3. Доказательства и воспроизводимость

Структура каталога: site.json, crawl.json, checks.json, run.json, raw/manifest.json и исходники. Имена исходных файлов строятся из внутренних ID, а не внешнего пути URL. Производный DOM и извлечённый текст имеют свои типы и source_evidence_id. Манифест записывается до артефактов, которые на него ссылаются.

Если верификация обязательных доказательств не проходит, соответствующие проверки не выдаются как достоверные. Ошибка диска сообщается явно. Исходный пользовательский PDF и данные другого запуска не перезаписываются.

### 14.4. Контракт для шага 2

Передать полезные и поддерживающие тексты, page/evidence ID, ограничения охвата, пользовательские материалы с происхождением, список вариантов языков/географии и technical checks. Шаг 2 обязан цитировать наблюдённый материал и не превращать неопределённую географию в установленный факт. Технические ограничения не исчезают после построения профиля.

# 15. Приёмка будущей реализации

### 15.1. Обязательные сценарии

| Сценарий | Проверяемый результат |
|---|---|
| Полезный одностраничник | limited; шаг 2 допустим; нет искусственного барьера 3 страниц |
| Три длинные служебные страницы | Недостаточность бизнеса не скрыта большим числом символов |
| robots разрешает главную, запрещает услуги | Решения различаются по URL; запрещённый GET не выполнен |
| robots 404 и robots 503 | Разные состояния; 503 не становится «всё открыто» |
| Внешний robots-редирект | Файл применён к первому origin; HTML scope не расширен |
| Несколько групп и пересекающиеся правила | Парсер и объяснение согласованы; номера строк верны |
| Sitemap отсутствует / повреждён / зациклен | Ссылки читаются; лимиты не превышены |
| Параметрическая ловушка | Очередь и число кандидатов ограничены |
| Повторяющиеся X-Robots-Tag | Все значения и адресаты сохранены |
| noindex на услуге, нет данных по другой странице | Первая проверка fail, вторая unknown |
| Google-Extended | Есть политика; нет выдуманного HTTP probe |
| JS добавляет основной текст | Сохранены оба представления и наблюдение роста |
| Браузер отсутствует / нет egress-контроля | Статический проход работает; JS unknown |
| UA получил 403, базовый запрос 200 | Описано конкретное наблюдение без обещания о реальном роботе |
| Пользовательское описание | Происхождение user_provided; технические fail не исправлены |
| Deadline / Retry-After за его пределом | Частичные результаты сохранены; задержка не игнорируется |

### 15.2. Проверка целостности

Сравнить HTTP-счётчики с журналом тестового транспорта. Проверить, что сумма состояний выбранных кандидатов объясняет coverage; повторные HTTP-попытки не добавляют страницы. Все evidence_id разрешаются в артефакты и хэши. Неизвестные и выключенные проверки имеют разные причины.

Тесты основного конвейера выполняются офлайн на фикстурах. Для браузера нужен контролируемый пример изменения DOM и отдельная проверка сетевого ограничения. Если browser integration не была реально запущена, это должно быть указано в отчёте разработки, даже если unit-тесты прошли.

### 15.3. Критерий завершения

Реализация готова к использованию в проекте, когда выдаёт согласованные JSON, соблюдает пределы, сохраняет доказательства и позволяет однозначно объяснить каждую пропущенную страницу и каждую проверку. Полный обход интернета и гарантированное установление причин GEO-видимости в этот критерий не входят.
