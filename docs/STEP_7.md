# Шаг 7: независимая выборочная проверка — offline MVP

Модуль `geo_audit.step7` принимает проверенный результат шага 6. Он готовит слепые задания, принимает явно переданный файл внешней проверки, проверяет его структуру/цитаты и измеряет согласие. Без API результатов модели не создаётся: status=pending_api_key, crosscheck.jsonl пуст, agreement_percent=null, reliability=not_assessed.

## Запуск

```powershell
.\.venv\Scripts\python.exe -m geo_audit.step7 `
  --step6-dir private/step6-review-20261102-002 `
  --output-dir private/step7-demo-002

.\.venv\Scripts\python.exe -m geo_audit.step7 --verify private/step7-demo-002
```

Откройте report.html в новой папке результата. Там видны объём выборок, пересечение, число уникальных заданий, готовность и показатели согласия. Это внутренний просмотр для аудитора, его нельзя отправлять слепому проверяющему. Страница не использует внешние ресурсы/JavaScript и экранирует исходные тексты.

Успешная подготовка или частичный импорт возвращают 0. Это не означает, что проверка модели выполнена. Невалидный источник, конфигурация, лимиты или ошибка публикации возвращают 2. Существующие папки и исходники не перезаписываются.

Текущая версия — step7-rules-2: сводка, слой изменений и publication manifest имеют схемы 1.1. Старые публикации rules-1 сохраняются для просмотра; для replay новой версией повторите обработку того же шага 6 в новую папку. Слепые задания и формат ReviewResult остаются 1.0: при неизменном источнике/seed задания сохраняют ID и payload, повторять модельные вызовы только из-за обновления кода не требуется.

## Как выбираются ответы

1. Рассматриваются ответы с measurement_eligible=true: пригодная доставка, вопрос допущен к измерению.
2. Все needs_model из этого множества включаются в проверку неопределённых случаев.
3. Независимо от них выбираются случайные ceil(5% × M) без возвращения из всего пригодного множества. При 445 ответах это 23, при 1000 — 50.
4. Обе части объединяются по answer_id. Пересечение не создаёт повторного задания и дополнительного расхода.

Перед выборкой ID сортируются, seed сохраняется (по умолчанию 20261103). Изменение порядка входных строк не меняет выборку. --seed позволяет явно изменить эксперимент. Исключённые из измерения вопросы и непригодные ответы не входят в M. Малый пилот с 4 ответами даёт только 1 случайный пример; это не достаточная оценка качества корпуса.

Список может включать needs_model из-за конфликтующих рангов. Однако шаг 7 проверяет только идентичность компании и роли брендов; ранги не исправляются и остаются rank_outside_review_scope. Полнота извлечения конкурентов тоже не становится подтверждённой автоматически.

## Что получает проверяющий

Только blind_jobs.jsonl и схему содержательного результата. Каждый job содержит непрозрачный job_id, хеш и оригинальный текст, исходный вопрос, минимальный профиль названий/доменов и фиксированную инструкцию.

В нём нет первичной разметки, уверенности, причин отбора, флага «случайный/спорный», исходного answer_id, поставщика/модели измеряемого ответа. selection.json и annotations не передаются проверяющему. Профиль не включает личные заметки и лишние авторские поля. Инструкции внутри анализируемых ответов считаются данными, ссылки не открываются.

Первичная разметка текущего шага 6 выполнена правилами, поэтому у неё нет модельного семейства. Если позже первичным исполнителем станет модель, проверяющий должен быть другого семейства; такую схему/адаптер нужно явно подключить, текущая версия не принимает неизвестные форматы первичного исполнителя.

## API пока отключён

В runtime нет SDK, чтения API-ключей и сетевых клиентов. Само появление ключа ничего не запустит. executor.json фиксирует executed=false и нулевые вызовы. Ключи и будущие live endpoints не принимаются из ответов/manifest.

Заявленные названия/семейства моделей импортируются из файла как provenance. Программа не наблюдала внешний вызов и не может доказать, что его действительно выполнил заявленный поставщик. При реальном API адаптер должен формировать metadata reviewer из собственной конфигурации/ответа сервера, а не доверять самоописанию модели. Конкретные API model IDs и цены сейчас не предполагаются.

## Как принять результаты позднее

```powershell
.\.venv\Scripts\python.exe -m geo_audit.step7 `
  --step6-dir private/step6-review-20261102-002 `
  --results private/reviewer-results.jsonl `
  --output-dir private/step7-import-001
```

Используйте тот же seed и тот же исходный шаг 6. Новый файл результата не меняет задания для тех же выбранных ответов. Код не перечитывает произвольные raw_ref и не отправляет ничего вовне.

Формат строки описан в schemas/step7/ReviewResult.schema.json. Основные поля: job_id, text_sha256, reviewer (kind/provider/model/family), status, target_presence, target_recommended, target_discouraged и brands. В brands передаются дословное имя, is_target, роли и отдельные массивы identity_evidence/recommendation_evidence/discouragement_evidence с quote/start/end. Допускаются обе роли=yes для разных сценариев.

Модель должна возвращать содержательную разметку; обёртка reviewer/status и связь с заданием формируются доверенным будущим адаптером. Для kind=model обязательны model и family. Ручной результат имеет kind=manual, тестовый — synthetic. Файлы examples/contracts/step7/*.synthetic.json иллюстрируют структуру, не назначены реальным jobs и будут отклонены как unassigned_job при случайной подаче без адаптации.

Все цитаты сверяются с точным оригиналом. Название должно быть в identity evidence; для целевой компании допускается каноническое имя с цитатой её явного алиаса. Проверка цитаты доказывает наличие текста, не истинность смыслового вывода. Отсутствие компании не требует выдуманной цитаты отсутствия.

Неизвестный job, другой хеш, ложная цитата, лишние поля или несогласованные роли отправляют строку в quarantine. Идентичный повтор — duplicate. Конфликтующие версии одного job отклоняются все; программа не выбирает удобную версию по порядку. Ошибка модели имеет status=error, nullable решения и ограниченный error_code; она остаётся незавершённым заданием, не отрицательным ответом.

Одна публикация оценивает один заявленный модельный состав: provider/model/family. Если успешные модельные результаты относятся к разным составам, все модельные записи этого смешанного импорта попадают в quarantine с причиной mixed_model_reviewers. Разделите уже полученный файл по исполнителям и импортируйте отдельно — повторные API-вызовы не нужны. Регистр/внешние пробелы provider и family не создают разные составы; model ID сохраняется точным. Ручные и synthetic-записи не участвуют в модельном согласии.

## Что исправляется, а что сохраняется

- Только первичное uncertain может уточняться принятым модельным/ручным решением yes/no.
- Повторное uncertain остаётся неразрешённым. Оно не входит в подтверждённые упоминания, но не переименовывается в no.
- Уверенные yes/no первой разметки не заменяются, включая случаи случайной проверки. Расхождения записываются отдельно.
- При конфликте идентичности компании неизвестные роли не уточняются по решению о другой сущности.
- Роли бренда не уточняются, пока сама его идентичность остаётся uncertain. Это поле явно сохраняется в outstanding_fields.
- Ранги и target_cited не пересматриваются: это вне двух задач данной проверки.
- Синтетические review-результаты можно принять для проверки формата, но они не меняют эффективные значения и не создают модельную надёжность.

resolved_annotations.jsonl — слой изменений, а не переписанный файл схемы шага 6. В каждой строке сохраняются answer_id, эффективные целевые признаки, field_sources, outstanding_fields, confident_disagreements и ссылки на review_job_id. brand_overrides содержит индекс исходного бренда, проверенное написание и только изменённые uncertain-поля; при разрешении неоднозначного алиаса потребителю нужно учитывать reviewed_name. Исходные цитаты правил остаются в input/annotations.jsonl, доказательства второй стороны — в crosscheck.jsonl. Новые бренды, пропущенные первым извлечением, автоматически не добавляются выборочной проверкой.

Число resolved_fields включает изменения целевых признаков и отдельных полей брендов, это не число ответов. Первичная разметка остаётся неизменной. Для шагов 8–9 нужно явно применить слой изменений, сохраняя provenance и неопределённость.

Каждая строка дополнительно привязана к SHA-256 точной первичной аннотации (primary_annotation_sha256, канонический encoded(model_dump(mode="json")) шага 6). Одного совпадения текста для применения изменений недостаточно. Источник каждого поля и job ID должны согласовываться. Расхождения уверенных ролей/идентичности отдельных брендов сохранены в brand_disagreements, без исправления исходных значений.

## Как считается согласие

Только на случайной части и только по исходным решениям шага 6, не по уже исправленным значениям. Спорная часть вне случайной выборки не добавляется к показателю согласия.

Три показателя независимы:

| Показатель | Единица сравнения |
| --- | --- |
| identity | Идентичность целевой компании в ответе |
| target_roles | Идентичность цели вместе с парой recommended/discouraged |
| competitor_roles | Та же пара для совпавшего имени кандидата-конкурента |

Сравниваются определённые yes/no; uncertain, ошибки, отсутствующие и ручные/синтетические результаты не выдаются за модельное совпадение. Роли цели сравнимы только при определённой идентичности обеих сторон. Для конкурентов используется точное NFKC/casefold-сопоставление имён, без самовольной fuzzy-склейки. Пропущенный проверяющим бренд снижает покрытие сравнения.

Разная идентичность цели означает расхождение target_roles даже при одинаковом no/no: совпавшее отсутствие рекомендаций о разных сущностях не подтверждает правильность роли нашей компании.

agreement_percent = 100 × matches / comparable; при нуле comparable — null. comparison_coverage = comparable / assigned_comparisons. Показываются все числители и знаменатели.

Порог исходного алгоритма: неокруглённое согласие ≥90% — средняя надёжность данного показателя, ниже — низкая и предупреждение. Для защиты от «100% на одном ответе» по умолчанию также нужны минимум 20 сравнимых пар и покрытие 80%; это явно заданная продуктовая политика, не статистическая гарантия. --minimum-comparable меняет минимум для контролируемых пилотов; ReviewPolicy содержит остальные настройки. При малом/неполном сравнении — insufficient_sample, без данных — not_assessed.

Учитываются и разные ответы: минимум minimum_distinct_answers, а если он не задан — тот же minimum_comparable. Таким образом 20 брендов из одного ответа не дают среднюю надёжность. comparable_answers показывается отдельно от числа пар. Для ролей конкурентов несколько сравнений могут относиться к одному ответу; повторные ответы одного вопроса тоже не гарантируют статистическую независимость.

Согласие не доказывает истинность разметки. Совпавшие ошибки двух исполнителей возможны. В импортированном режиме происхождение модели заявлено файлом, а не проверено сетью. Эти проценты не являются показателями видимости компании.

## Артефакты и ограничения

В публикации: input со снимками источника/политики/результатов, selection.json, blind_jobs.jsonl, crosscheck.jsonl, review_intake.jsonl, quarantine.jsonl, resolved_annotations.jsonl, agreement.json, summary.json, executor.json, validation.json, report.html и последний manifest.json. Общий storage также создаёт пустой raw/.

В quality.json отдельно указаны оставшиеся неопределённые ответы, расхождения, ранги вне области проверки, причины карантина и заявленный проверяющий. Ожидание результата и неразрешённый смысл — разные счётчики. В HTML есть таблицы «было / стало / источник» и журнал отклонённых строк. Даже при получении всех назначенных результатов итог остаётся partial, если импорт содержит карантин или ошибки.

Контракт слоя изменений — schemas/step7/ResolvedAnnotation.schema.json. В HTML длинные задания показаны как явно помеченный preview: до 2048 символов ответа и 512 символов вопроса. В слепых заданиях и входных снимках тексты полные; цитаты проверяются по полным оригиналам.

Вход шага 6 предварительно проходит replay-проверку, затем захваченные файлы/manifest снова сверяются с воспроизведёнными артефактами. Публикация шага 7 новая, атомарная, с confined I/O и хешами. --verify пересобирает все результаты из сохранённых снимков, не пишет и не делает внешних запросов. Manifest-пути не используются как произвольные пути чтения.

Сохраняются лимиты исходных стадий: до 10 000 строк, 64 MiB файлов ответов/результатов, 1 MiB строки результата, очередь до 64 MiB, любой артефакт до 64 MiB, публикация до 256 MiB. Схемы и synthetic examples хранятся в Git; реальные результаты и ключи — только ignored private/.

Общий импорт ограничен также 50 000 фрагментов доказательств. Нормализованное представление каждой цитаты создаётся один раз, а не заново для каждого алиаса.

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_step7.py -q
.\.venv\Scripts\python.exe -m ruff check src/geo_audit/step7 tests/test_step7.py tools/generate_step7_schemas.py
.\.venv\Scripts\python.exe -m mypy src/geo_audit/step7
.\.venv\Scripts\python.exe tools/generate_step7_schemas.py
```

Шаги 8–12 не запускаются автоматически. До подключения настоящего проверяющего текущий результат — готовая очередь и честный статус ожидания, не выполненный независимый аудит.
