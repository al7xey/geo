## Главный вывод по HTTP и HTTPS

HTTP подходит для чтения публичного сайта. HTTPS следует проверять первым при вводе адреса без схемы: это позволяет проверить защищённую версию и увидеть штатный редирект. Доступность по HTTP и исправность HTTPS являются разными результатами. Неработающий HTTPS не должен автоматически означать, что сайт невозможно обследовать.

Политика ниже — предложение для нашего продукта, а не требование HTTPX:

| Ввод / ответ | Действие |
|---|---|
| `example.com` | Сначала `https://example.com/`; HTTP допустим как запасная попытка при транспортной ошибке HTTPS |
| Явный `http://example.com/` | Проверить указанный URL и его редиректы; HTTPS проверить отдельно, если фактически не был проверен |
| Явный `https://example.com/` | Проверить этот URL с проверкой сертификата; при транспортном сбое разрешить отдельную попытку HTTP с сохранением ошибки и отметкой о смене схемы |
| HTTP перенаправляет на исправный HTTPS | Использовать конечный HTTPS URL |
| HTTPS недоступен, HTTP читается | Продолжить по HTTP с предупреждением и ограничениями достоверности содержимого; не объявлять HTTPS исправным |
| HTTPS дал 401/403/404/429 или страницу проверки браузера | Не переключаться на HTTP автоматически ради обхода такого ответа |
| HTTPS перенаправляет на HTTP | Зафиксировать понижение схемы; продолжение допустимо только в разрешённой области сайта и с предупреждением |
| Обе схемы не дали пригодной страницы | Сохранить результаты попыток и конкретную причину; не запускать последующие платные этапы |

HTTP fallback включён в предлагаемой конфигурации; у него должен быть явный переключатель. Он не использует `verify=False`. Ошибка сертификата, отказ соединения, DNS-ошибка и таймаут имеют разные коды. Таймаут не доказывает отсутствие HTTPS. Если HTTP ведёт обратно на неисправный HTTPS, запасной путь не сработал.

## Шаг 0. Проверка входного адреса и доступности

### Вход

Строка с адресом; конфигурация; при необходимости явно заданные дополнительные допустимые хосты. На первой версии это публичные HTTP(S)-сайты на стандартных портах. Поддержка других портов — отдельная настройка, а не автоматическое расширение.

### Нормализация

- Удалить внешние пробелы, разобрать URL библиотечным парсером, проверить корректность IDN и портов.
- Разрешить только HTTP/HTTPS. Отклонить встроенные логин/пароль, пустой хост и некорректные адреса.
- Сохранить исходный ввод, явно указанную схему, путь и query; удалить fragment. Не отбрасывать значимый `/ru/`, `/services/` или query и не менять регистр пути.
- Хост нормализовать; не склеивать произвольно разные поддомены и не считать канонический URL из HTML приказом сменить область обхода.
- Раздельно хранить `input_url`, `normalized_url`, `effective_url`, `origin` и `crawl_scope`. Origin включает схему, хост и порт; robots.txt запрашивается от корня origin, а не от пути входной страницы.

### Запросы и редиректы

Использовать ограниченный GET: HEAD не даёт содержимого, нужного для оценки HTML. Редиректы обрабатывать вручную, проверяя каждый следующий адрес до запроса. Хранить URL, код ответа и Location каждого перехода, а также смену схемы.

Переходы на том же хосте допустимы. Наблюдаемый редирект между `www` и вариантом без `www` можно считать техническим алиасом только при корректной проверке границы домена с учётом публичных и частных суффиксов. Другие поддомены не добавляются автоматически. Совпадения регистрируемого домена недостаточно для разрешения всех его поддоменов, особенно на многопользовательском хостинге.

При редиректе страницы на другой неподтверждённый хост остановиться до запроса назначения и вернуть `needs_input`, целевой URL и основание. CLI принимает повторный запуск с явным `--allow-host`; библиотека сама вопросов в консоли не задаёт. Не создавать цикл интерактивных подтверждений внутри обхода.

Без схемы применить HTTPS-first и ограниченный HTTP fallback из таблицы. Для явной схемы не менять входное намерение незаметно: отдельная попытка должна иметь собственную запись и признак fallback. Не перебирать все комбинации `www`, схем и доменов вслепую.

### Пригодность ответа

Код 200 сам по себе недостаточен. Проверить конечный статус, тип содержимого и наличие HTML; при отсутствующем или ошибочном Content-Type допустима ограниченная проверка начала документа с отдельной отметкой. 204 и бинарный файл не являются страницей для чтения. Признаки CAPTCHA, WAF challenge, страницы входа и soft-404 сохранять с уровнем уверенности; не выдавать эвристику за доказательство.

HTML с оболочкой JS-приложения допускается к ограниченной диагностике шага 1. Малое количество текста на входной странице не останавливает анализ автоматически. Если передан глубокий путь и он не работает, не заменять его молча корнем сайта: сохранить проблему и вернуть её явно.

### Результат `site.json`

Метаданные запуска и версии схемы; все входные и конечные URL; разрешённые хосты; список попыток и редиректов; статусы транспорта и TLS; полученный HTML с ID доказательства; тип содержимого; предупреждения; `status = ok | partial | needs_input | failed`; `can_crawl`; список причин. Связь `can_crawl` и статуса должна быть формально задана, а не выведена из одного HTTP-кода.

Непрочитанный текст не равен недоступности сервера. Сетевая недоступность, отказ сервера и недостаточность текста различаются. Результат шага 0 повторно используется шагом 1 без лишнего GET.

## Шаг 1. Ограниченный обход и техническая диагностика

### 1.1. Собственная политика обхода и robots.txt

У скрипта собственный честный User-Agent, например `GEOAudit/0.1`. Правила для своего обхода отделены от оценки директив для сторонних роботов. Не подменять имя собственного обходчика, чтобы обойти Disallow. Один адрес, явно введённый пользователем, проверяется на шаге 0; дальнейший автоматический обход подчиняется выбранной политике robots.

Сохранить исходный robots.txt, HTTP-результат и номера строк. Для каждого релевантного URL оценивать правила для конкретного токена робота; не давать всему сайту единое «робот разрешён», если пути имеют разные правила. Применять парсер с проверенной семантикой выбора группы, Allow/Disallow, wildcard и специфичности; не заменять его поиском строки Disallow.

Предлагаемая обработка: 404/410 — файл отсутствует, явного запрета нет; 5xx/сеть после ограниченных повторов — состояние неизвестно, автоматический обход приостановлен. Для 401/403, 429, невалидного содержимого и прочих статусов задать отдельную консервативную политику и код причины. Не записывать техническую ошибку как директиву владельца `Disallow: /`.

RFC 9309 допускает переходы robots.txt между хостами. Такие переходы можно обработать отдельно от редиректов страниц: до пяти безопасных публичных переходов, с сохранением начального origin как области действия правил. Чужой хост с файлом robots.txt не расширяет область обхода HTML-страниц. Если ограничение безопасности не даёт прочитать файл, результат неизвестен.

### 1.2. Реестр роботов

Число 14 из PDF пока не обосновано перечнем. Вместо него нужен конфиг с документированными записями: оператор, robots-токен, назначение, HTTP User-Agent при его наличии, особенности применения правил, ссылка на документацию, дата проверки. Не дополнять список выдуманными токенами ради количества.

Для минимальной версии обоснованы группы OpenAI (`OAI-SearchBot`, `GPTBot`, `ChatGPT-User`), Anthropic (`Claude-SearchBot`, `ClaudeBot`, `Claude-User`) и Google (`Googlebot`, `Google-Extended`). Поиск, обучение и загрузка по запросу пользователя — разные назначения. Отдельно учитывать особенности каждого провайдера. Например, OpenAI указывает, что robots.txt может не применяться к пользовательским загрузкам ChatGPT-User; это не повод выдавать запрет для этого токена за гарантированную недоступность продукта.

Google-Extended — токен управления использованием контента, без собственного HTTP User-Agent. Не отправлять запросы от его имени и не трактовать его запрет как запрет Google Search. Дополнительные поисковые роботы подключаются по мере документирования их роли в проекте.

### 1.3. Поиск и отбор страниц

Объединить URL из входной страницы, внутренних ссылок, Sitemap-директив robots.txt и ограниченного списка стандартных sitemap-путей. Поддержать `urlset`, `sitemapindex`, namespaces и gzip в пределах лимитов. При ошибке или отсутствии sitemap продолжать по внутренним ссылкам. Sitemap является способом обнаружения URL, а не доказательством индексирования.

Очередь приоритетов: входная/главная, о компании, услуги/продукты, цены, контакты, FAQ. Сохранить причину отбора, реальный язык страницы и URL-источник обнаружения. Не следовать logout, корзине, поисковым формам, календарям и бесконечным параметрическим комбинациям. Выполнять только GET; формы не отправлять.

До 30 различных HTML-кандидатов, включая входную страницу; неудачный кандидат расходует слот, чтобы очередь не стала бесконечной. Редирект-алиасы не создают новые страницы. Все дополнительные сетевые операции учитываются общим бюджетом. Сохранять число найденных, выбранных, загруженных, прочитанных и пропущенных URL, причины пропуска и факт остановки по лимиту. Canonical — сигнал для анализа дубликатов, а не безусловное доказательство равенства страниц.

### 1.4. Извлечение и происхождение текста

Сохранить исходный HTML отдельно от извлечённого текста. Извлекать основной контент trafilatura; при неудаче применять BeautifulSoup с исключением скриптов, стилей и явного служебного содержимого. Не терять значимые заголовки, списки и таблицы цен при запасном разборе. Хранить метод извлечения, title, заголовки, длину текста, хэш, ID исходного документа и версию обработки.

Нельзя делать вывод «нужной страницы нет на сайте» только потому, что её нет среди 30 прочитанных URL.

### 1.5. JavaScript

Малый статический текст — повод проверить страницу, но не диагноз. Для максимум пяти подозрительных страниц сравнить извлечение из исходного HTML с текстом DOM после ограниченного рендеринга. Сохранить оба результата и точный режим. Зафиксировать наблюдение: текста стало заметно больше, различий не выявлено либо измерение не удалось. Порог различия — настраиваемая эвристика.

Не выводить «все нейросети не видят JavaScript» и не объявлять сайт зависимым от JS только по наличию тега script. Рендеринг не применяется для обхода авторизации или CAPTCHA. Если Playwright/браузер не установлен, соответствующая проверка получает `unknown`, остальные этапы продолжаются. Браузерный модуль необязателен.

### 1.6. HTTP-заголовки и метаданные

По каждой странице сохранить все применимые meta robots, robot-specific meta и все заголовки X-Robots-Tag, включая повторяющиеся. Различать общие и адресованные конкретному роботу директивы. Не терять `noindex`, `none`, `nosnippet`, `max-snippet`, `data-nosnippet` и относящиеся к области исследования ограничения; интерпретацию связывать с документированным провайдером.

Robots.txt ограничивает обход, noindex — индексирование, ограничения фрагментов — использование/показ текста в конкретных продуктах. Эти проверки не заменяют друг друга. Наличие noindex на контактах и на всех основных услугах требует разных выводов; абсолютные обещания об исчезновении бренда из ответов запрещены методикой.

### 1.7. Проверка различий по User-Agent

Основной результат — анализ robots без дополнительных запросов от каждого робота на каждую страницу. Ограниченные сравнительные GET по документированным HTTP User-Agent сделать отключаемой диагностикой, максимум на трёх выбранных страницах и для трёх агентов. Включать её только при возможности соблюсти применимые правила и общий бюджет.

Сравнивать конечный статус, URL, тип, признаки challenge и нормализованное содержание; динамическое отличие HTML само по себе не означает блокировку. Результат формулировать «при запросе из среды аудита с таким User-Agent получен X». Ни успех, ни отказ с подставленным заголовком не доказывает доступ реального робота с другой инфраструктуры.

### 1.8. Язык, страна и достаточность материала

Хранить язык страницы и признаки из lang/hreflang, контактов и домена. Страну компании, территорию услуг и рынок будущего измерения не смешивать. Доменная зона — слабый сигнал. Допустимы несколько языков/стран и неизвестное значение; конфликтующие признаки не разрешать произвольным выбором.

Порог «три страницы по 300 символов» оставить диагностическим ориентиром, а не обязательным пропуском к следующему шагу. Для первой версии предложено: хотя бы одна успешно извлечённая содержательная страница с 300+ символами даёт доступный материал; менее трёх таких страниц отмечается как ограниченное покрытие. Это эвристика, а не гарантия достаточности профиля. Длинный служебный текст не считается подтверждённым описанием бизнеса.

Если полезного материала недостаточно, вернуть `needs_description` и причины. Описание компании принимается отдельным аргументом/файлом от пользователя и хранится с `source_type=user_provided`; оно не делает технические проверки успешными. Библиотека не зависает в ожидании ответа. Данные до сбоя сохраняются.

### Результаты

- `crawl.json`: метаданные запуска; конфигурация и охват; список страниц с текстами, метаданными, состояниями и ID доказательств; сведения о sitemap; языковые/географические сигналы; итоговая достаточность материала.
- `checks.json`: проверки с `check_id`, областью URL/робот, `status = pass | fail | warning | unknown | not_applicable`, наблюдением, основанием, ID доказательства, временем и ограничением интерпретации.
- `raw/`: исходные HTML, robots, sitemap и при необходимости rendered DOM, с хэшами и манифестом. Полученные от сервера байты и результат декодирования/распаковки должны быть различимы; не называть производный DOM сырым HTTP-ответом.
- `run.json`: общий статус, затраченные лимиты, продолжительность, причины частичного результата и рекомендуемое следующее действие.

Все JSON имеют `schema_version` и `run_id`; результаты валидируются и записываются атомарно в отдельную папку запуска. У каждой ошибки есть машинный код и понятное объяснение. Частичная ошибка не уничтожает успешные результаты.

## Предлагаемые стартовые лимиты

Это настраиваемые параметры нашей реализации, а не нормативы протоколов.

| Параметр | Начальное значение |
|---|---|
| HTML-кандидаты | 30, включая входной |
| Конкурентные запросы на хост | 2; начало запросов не чаще одного в секунду |
| Дополнительные повторы временной ошибки | 2; учитывают Retry-After и общий лимит времени |
| HTTPX connect/read timeout | 5/15 секунд; дополнительно общий deadline операции |
| Redirect hops | 5 на цепочку, в общем бюджете |
| HTML | До 5 MiB после распаковки |
| robots.txt | До 512 KiB; превышение явно отмечается |
| Sitemap | До 5 файлов суммарно, до 5 MiB распакованного текста каждый, до 5000 URL суммарно |
| Browser rendering | До 5 страниц, до 20 секунд на страницу |
| UA probes | По умолчанию выключены; максимум 3 страницы × 3 агента |
| Общий HTTP-бюджет без браузера | 150 запросов, включая повторы и каждый redirect hop |
| Общий бюджет браузера | 200 HTTP(S)-запросов суммарно; превышение прерывает рендеринг с отметкой |
| Общая продолжительность запуска | 5 минут; после дедлайна частичные результаты сохраняются |

Предусмотреть лимиты декомпрессии, число URL в очереди и безопасный XML-разбор без внешних сущностей. Не повторять автоматически постоянные 4xx и ошибки сертификата. Не обходить 401/403 сменой User-Agent. Длительный Retry-After должен приводить к переносу/частичному результату в рамках дедлайна, а не игнорированию задержки.

## Границы сетевого доступа

Проверять публичность адреса до каждого запроса, включая редиректы, sitemap и браузерные подзапросы. Запрещены localhost, private, link-local, зарезервированные адреса и встроенные credentials, включая IPv6 и DNS-ответы. Один DNS precheck не защищает от DNS rebinding: нужна привязка проверенного назначения к соединению либо доверенный egress-фильтр. Не заявлять полную защиту на основании одной проверки строки URL.

Для первой локальной версии HTTP-клиент должен иметь проверяемую политику назначения. Браузерный режим включается только с эквивалентным контролем фактических соединений; если это не реализовано в среде, он остаётся выключенным с `unknown`, а не молча получает доступ во внутреннюю сеть. Не отключать TLS-проверки ни в HTTPX, ни в браузере. CDN-ресурсы могут быть публичными и внешними, но не становятся страницами обхода.

## Проверка будущей реализации

Основные проверки — воспроизводимые офлайн-сценарии с HTTPX MockTransport/тестовыми транспортами и фикстурами. Безопасность адресов, выбор схемы, границы хостов, robots, лимиты и частичные результаты проверять независимо от публичных сайтов. Для браузера нужен контролируемый пример с изменением DOM; интеграционный тест может использовать изолированный тестовый транспорт/egress и тестовое исключение только внутри тестов, без production-флага «разрешить всё».

Никаких платных API и шагов 2–12. Результат реализации — небольшой Python-пакет с CLI, который можно импортировать в будущий проект. Одна команда запускает шаги 0–1, но сетевой клиент, правила и сбор данных разделены по модулям.
