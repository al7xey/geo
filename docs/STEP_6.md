# Шаг 6: предварительная смысловая разметка без API

Модуль `geo_audit.step6` принимает завершённую публикацию шага 5, определяет явное присутствие целевой компании и её роль локальными правилами, сохраняет цитаты и задания для неоднозначных случаев. Исходники шага 5 не изменяются. Сеть, браузер и API-ключи не используются.

Это ограниченный offline baseline, не универсальный языковой анализатор. Все решения имеют method=rules и independent_review=not_performed. Точная цитата подтверждает текст, но не достоверность утверждения о компании и не безошибочность интерпретации.

## Запуск и просмотр

```powershell
.\.venv\Scripts\python.exe -m geo_audit.step6 `
  --step5-dir private/step5-review-20261102-002 `
  --output-dir private/step6-demo-002

.\.venv\Scripts\python.exe -m geo_audit.step6 --verify private/step6-demo-002
```

Выходная папка должна быть новой и отдельной от шага 5. После запуска откройте `report.html` в ней. Страница показывает решения по каждому ответу, роли и цитаты, полный исходный текст; есть поиск и фильтры. Она автономна: без CDN и внешних ресурсов, тексты экранированы, CSP разрешает фиксированные CSS/скрипт по хешу.

Успешная offline-обработка возвращает 0, включая штатное ожидание модели. Тогда summary.status=partial и pending_model содержит число заданий. Код 2 означает невалидный источник или ошибку публикации. `--verify` ничего не записывает.

Текущая версия — `step6-rules-2`, схемы и publication manifest 1.1. Старые результаты rules-1 остаются доступными для просмотра, но не проходят replay новой версией. Для обновления повторите обработку того же шага 5 в новую папку; исходники и старые публикации не перезаписываются.

## Поля annotations.jsonl

Каждому принятому на шаге 5 answer_id соответствует одна строка:

- target_presence: yes/no/uncertain — компания явно идентифицирована по словарю, не найдена или идентичность неясна;
- target_recommended и target_discouraged — независимые признаки положительного и отрицательного совета;
- target_cited — наличие целевого hostname в переданных citations, не проверка конечной страницы за redirect;
- answer_kind: list/prose/refusal для распознаваемых структур; контракт резервирует mixed/unknown;
- relevance=unassessed — достоверная автоматическая проверка «по теме/не по теме» пока не выполняется;
- brands: целевой бренд и кандидаты имён из списков/таблиц, их роли, цитаты и rank при явном рейтинге;
- reason_codes, method, status, needs_model, delivery_status, measurement_eligible и привязка к оригиналу.

Для error/empty/truncated признаки null, бренды пусты, статус not_eligible. Ошибка не становится отрицательным наблюдением. Вопрос с visibility_eligible=false может получить разметку для просмотра, но measurement_eligible=false исключает его из будущих показателей видимости.

Здесь нет придуманных confidence или вероятностей. no — вывод ограниченных правил о тексте, не гарантия отсутствия любой неявной рекомендации. Неопознанные перефразировки способны дать ошибки; независимый контроль остаётся нужен.

## Что определяют правила

1. Уникальный вариант названия вне URL даёт предварительное presence=yes. Общеупотребительные варианты нужно заранее внести в ambiguous_aliases профиля.
2. Нераскрытое сокращение даёт uncertain. Соседства короткого и полного имён недостаточно; поддержана явная связь вроде «под FKL понимается Факел».
3. Прямые конструкции «рекомендую X», «советую выбрать X», «не рекомендую X», «не стоит выбирать X» связываются с конкретным совпадением названия.
4. Список под явным заголовком «Рекомендованные сервисы» допускает положительную роль. Обычный нумерованный список её не доказывает.
5. Чужие цитаты, код, сложное отрицание, вопросы, местоимения и косвенные советы оставляются uncertain, если явного нейтрального объяснения недостаточно.
6. Для разных сценариев в одном ответе возможны обе роли=yes с отдельными доказательствами. Общий sentiment их не заменяет.
7. Ранг берётся только из нумерованного перечня с явным заголовком рейтинга. Конфликт рангов одного бренда даёт rank=null и задание модели.
8. Источник сам по себе не означает рекомендацию/упоминание в тексте. Совет выбрать сервис только по целевому URL оставляет идентичность uncertain.

Контекст теперь ограничивается конкретным фрагментом: нейтральная фраза об одном упоминании не отменяет неопределённость другого. Заголовок рейтинга/рекомендованного списка действует только на связанный с ним блок; обычный абзац или новый заголовок заканчивает блок. Поддерживаются Markdown-выделение имён и кавычки вокруг самого названия; цитата целого чужого совета сохраняет неопределённость. Определение одного сокращения не раскрывает другие сокращения.

Список конструкций намеренно ограничен. Код не гарантирует распознавание свободных формулировок, всех неявных названий или всех типов ответов. Наличие слова «рекомендую» где-то рядом с брендом недостаточно для положительного решения.

## Конкуренты и цитаты

Другие имена извлекаются как кандидаты из первых ячеек таблиц и пунктов списков с простыми ограничениями формы. Это не полное извлечение компаний из произвольного текста; обычная фраза в таблице может оказаться кандидатом. competitor_extraction=structured_candidates_only. Пропуск имени не доказывает отсутствие конкурента. Подтверждение сущностей/склейка вариантов относятся к шагу 8.

Роли кандидатов обрабатываются теми же правилами. Неясный конкурент тоже может создать задание, даже если роль целевой компании уже понятна.

Каждая положительная роль имеет Evidence: quote, start, end, rule. Перед публикацией проверяется `original_text[start:end] == quote`. Позиции — Unicode code points Python. Каноническое имя целевого бренда может отличаться от его алиаса в дословной цитате. Отсутствие не подкрепляется выдуманной цитатой; mentioned не означает recommended.

Для списка evidence содержит только сам пункт, а context_evidence — отдельную исходную цитату заголовка. Для ранга сохраняется rank_context_evidence. Цитаты не склеиваются и не растут вместе со всеми предыдущими пунктами списка. identity_basis отличает словарь целевой компании от неподтверждённых кандидатов названий. Контракты отклоняют противоречия между ролью и доказательствами, ранг без контекста, скрытую неопределённость и несходящиеся счётчики.

Проверка структуры и цитат не является независимой смысловой перепроверкой шага 7.

## Заглушка модели

На каждый неоднозначный ответ формируется одно semantic job со стабильным job_id, answer_id/text_sha256, исходным текстом и вопросом, профилем названий/доменов, requested_fields, версией инструкции и synthetic-флагом. Длинная заметка профиля не передаётся.

job_id зависит также от профиля, вопроса, запрошенных полей и инструкции: изменение контекста не переиспользует идентификатор старого задания. Кеширование реальных ответов моделей пока не реализовано; при его добавлении отдельно учитываются фактические provider/model.

Все задания имеют status=pending_api_key и executed=false; executor.json фиксирует disabled. SDK не импортируются, ключи окружения не читаются, задания не исполняются. Само добавление ключа ничего не запустит: live-адаптер и приёмку его результатов нужно подключить отдельно.

В шаге 7 неопределённые случаи следует объединить с заданиями проверки без повторной оплаты за одно и то же разрешение. Если первичная разметка когда-либо выполнялась моделью, независимость требует другого исполнителя. Сейчас нет фиктивных результатов модели, crosscheck и процента согласия.

## Файлы

```text
step6-result/
  input/prompts.json
  input/target.json
  input/answers.jsonl
  input/mechanical.jsonl
  input/step5-manifest.json
  annotations.jsonl
  semantic_jobs.jsonl
  executor.json
  summary.json
  quality.json
  validation.json
  report.html
  manifest.json
```

Общий storage также создаёт пустой raw/. Входные снимки позволяют воспроизвести результат автономно и не меняют оригинальную публикацию. Runtime не читает oracle.

Сводка содержит количества решений, не проценты видимости. Знаменатели, macro/micro и исключения будут реализованы на шаге 9. Непригодные по доставке записи не входят в счётчики yes/no/uncertain. measurement_eligible надо отдельно учитывать в будущих метриках, счётчики текущей сводки описывают разметку всех пригодных текстов.

quality.json содержит все состояния yes/no/uncertain, охват по measurement_eligible и причины очереди. Причины могут пересекаться внутри одного ответа, это не дополнительные платные запросы. В HTML они объясняются по-русски; доступны фильтры положительных, отрицательных и смешанных советов. Для полностью пустого/непригодного входа итог partial.

Четыре категории «факт / оценка / гипотеза / рекомендация аудита» сохраняют прежний смысл. Шаг 6 создаёт отдельный слой интерпретации ролей; совет чужой модели не становится рекомендацией аудита. Весь текст ответа по этим четырём категориям не классифицируется.

## Целостность и безопасность

Проверяются commit шага 5, хеши захваченных файлов, fingerprint и воспроизводимость mechanical из тех же снимков. Поддерживается текущий формат шага 5; для чужого экспорта нужен адаптер.

Выход — новая папка, confined I/O, атомарные файлы, manifest последний. raw_ref/URL и пути из ответов не открываются. Верификация шага 6 использует фиксированные имена, проверяет размеры/хеши и пересобирает результат из снимков. Она подтверждает согласованность, не подлинность внешних ответов.

Наследуются входные лимиты шага 5. Аннотации и очередь ограничены 64 MiB каждая при построении, любой файл — до 64 MiB, весь результат — до 256 MiB. Превышение бюджета отклоняется до публикации. Сеть, DNS, paid API и браузер не запускаются.

Кавычки, код и границы списков индексируются один раз для каждого ответа. Проверка контекста не перечитывает весь предыдущий текст для каждого совпадения; доказательства длинных списков имеют линейный объём. Стабильный job_id учитывает также версию правил и схемы, чтобы новая разметка не переиспользовала старое задание по ошибке.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_step5.py tests/test_step6.py -q
.\.venv\Scripts\python.exe -m ruff check src/geo_audit/step6 tests/test_step6.py tools/generate_step6_schemas.py
.\.venv\Scripts\python.exe -m mypy src/geo_audit/step6
.\.venv\Scripts\python.exe tools/generate_step6_schemas.py
```

Проверяются прямые/отрицательные/смешанные роли, сокращения, цитаты, косвенная речь, вопросы, списки/ранги, URL, инструкции внутри данных, ошибки доставки, handoff, целостность и неизменность источника. Правила тестируются также на бренде вне мок-набора. Oracle читается тестом только после runtime; результаты на синтетических шаблонах не доказывают качество на реальных ответах. Автоматического перехода к шагам 7–12 нет.
