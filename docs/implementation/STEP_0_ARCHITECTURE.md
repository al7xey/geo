## Объём реализации

Создан локальный Python-пакет с контрактами и CLI. Работают нормализация URL без сети,
проверка конфигурации и результатов, генерация схем, базовая политика допустимости fallback,
общий бюджет, локальное хранение/проверка доказательств, сериализуемая передача шагу 1.

`validate_site` и `geo-audit step0` **всегда** возвращают ошибку реализации до I/O.
Не создан ни один результат реального аудита. Это намеренная граница текущего поручения:
основа реализации и проверяемые контракты. Интерфейсы сети являются `Protocol`,
без фиктивных реализаций `GET` и без создания обычного HTTPX-клиента под видом защищённого.

## Почему async, но последовательно

Публичный API - `async def validate_site(input_url, config, client, budget, *,
destination_checker, store) -> SiteValidationResult`. Будущий исполнитель использует
`HTTPX.AsyncClient` с отдельным защищённым транспортом. Один запрос выполняется за раз.
Async нужен для отмены всего ожидания через `asyncio.timeout` по монотонному дедлайну:
DNS, соединение, весь поток тела, backoff и ограничение частоты. HTTPX read timeout
ограничивает ожидание очередных данных и не заменяет этот дедлайн.
Синхронный `httpx.Client` потребовал бы отдельного механизма остановки медленного потока.
CLI станет синхронной оболочкой `asyncio.run`; вложенный loop в библиотеке не создаётся.
Сейчас async-оркестрация явно недоступна, механизм отмены пока не заявляется реализованным.

Проверенный контракт бюджета предназначен для одного последовательного запуска, не для
конкурирующих задач. Считать попытку нужно непосредственно перед запуском транспорта:
отказ соединения и TLS failure расходуют попытку; отклонение назначения до транспорта - нет.
`request_sent` означает запуск транспортной попытки, а не доказательство отправки HTTP-байтов.
Каждый retry, redirect GET и fallback учитываются отдельно.

## Версии, обязательность и null

| Версия | Значение | Когда менять |
|---|---|---|
| Пакет | `0.1.0` | Код и API |
| Схема | `1.0.0` | Структура/семантика сериализованных контрактов |
| Алгоритм | `step0-1.0` | Методика нормализации, fallback, области, пригодности |
| Конфигурация | `step0-config-1.0.0` | Состав параметров и defaults |
| Конкретная конфигурация | `config_sha256` | SHA-256 канонического JSON полного Step0Config |
| PSL | `RedirectHop.psl_sha256` | Хэш локального снимка с private-секцией, когда принят www-алиас |

Пример исходного алгоритма с `schema_version="1.0"` является сокращённой учебной записью.
Первая полная программная схема получила **`1.0.0`**, поэтому этот фрагмент не принимается
как полный `SiteValidationResult`. Он развёрнут в полные синтетические примеры в
`examples/contracts`. Миграция усечённых записей не имитируется.

Все поля выходных моделей обязательны. Nullable-поле также обязательно присутствует,
даже если значение `null`. Defaults есть только у `Step0Config`. Полный список полей,
обязательности, типов и `null` автоматически выпущен в `STEP_0_FIELDS.md` и JSON Schema.
Неизвестные поля запрещены; строгая проверка не превращает строку `"false"` в bool.
Числа должны быть конечными. Времена - aware UTC с нулевым смещением, длительности -
неотрицательные секунды/миллисекунды. Исходная временная зона сохраняется отдельно.

Ключевые случаи null:

- До успешной нормализации `normalized_url`, `input_scheme_explicit`,
  `input_host_unicode`, `entry_path` равны null; это не попытка обратиться к корню.
- Без разрешённой передачи выбранного HTML `effective_url`, `origin`,
  `selected_evidence_id` равны null. Полученный непригодный ответ остаётся в attempts/evidence.
- `status_code=null` означает отсутствие HTTP-ответа, а не код 0. `transport_error=null`
  означает отсутствие транспортной ошибки, а не пригодность контента.
- `resolved_target=null` возможен, если запрос отклонён до транспорта; `connected_ip=null`
  возможен, если соединение не установлено. Для transport start проверенное назначение обязательно.
- `parent_attempt_id=null` только у initial; `parent_run_id=null` у независимого запуска.
- `raw_location`/`target_url` могут быть null у отвергнутого некорректного redirect.
- Кодировки могут быть null, когда неизвестны/декодирование не производилось.
- `proposed_target_url` не null только для needs_input после наблюдаемого внешнего redirect.

ID - локальные непрозрачные строки безопасного алфавита. URL хранится целиком только в
локальных данных; консоль не выводит произвольный URL/query из ошибок.
Списки представлены неизменяемыми tuple в Python и массивами в JSON.

## Полная таблица состояний и can_enter_step1

`status`: **ok, partial, needs_input, failed**. Других состояний результата нет.

| Наблюдение | content_state | status | can_enter_step1 |
|---|---|---|---|
| Полный HTML 200, без существенных ограничений | html | ok | true |
| Полный HTML 200 через fallback / наблюдаемый downgrade / иное явное ограничение | html | partial | true |
| Полный HTML 200, кандидат JS-приложения | js_candidate | partial | true |
| Полный HTML 200, подозрение на challenge/soft-404; диагностика явно разрешена | suspicious_html | partial | true |
| То же, диагностика не разрешена | suspicious_html | partial | false |
| Подтверждённый challenge/логин при 2xx | access_barrier | partial | false |
| Пустой ответ, включая 204 | empty | partial | false |
| Не HTML при 2xx | non_html | partial | false |
| Усечённый/повреждённый поток с ответом 2xx | incomplete | partial | false |
| Превышение лимита тела с ответом 2xx | too_large | partial | false |
| 401/403 после политики запросов | http_denied | failed | false |
| 404/410 | http_missing | failed | false |
| 408/429/5xx после допустимых повторов | http_unavailable | failed | false |
| Иной неподдерживаемый HTTP-статус, включая 206 и незавершённый redirect | http_other | failed | false |
| Безопасный внешний redirect вне scope | http_other | needs_input | false |
| Ошибка ввода/назначения, NXDOMAIN, окончательный сетевой провал без ответа | not_received | failed | false |
| Дедлайн/бюджет до пригодного результата | последний наблюдаемый либо not_received | failed | false |
| Ошибка обязательного сохранения | последний наблюдаемый | failed | false |

Для 206 выбрана консервативная политика: частичный диапазон не является полной входной
страницей. Сам по себе явный HTTP с полным HTML не требует partial: предупреждение о
незашифрованном канале относится к пользовательскому выводу, HTTPS остаётся not_observed.
Если добавляется существенная транспортная причина, результат partial и причина обязательна.

Общие необходимые условия true: status ok/partial, состояние html/js_candidate либо
разрешённое suspicious_html; полный непустой `entity_bytes`, HTTP 200 без ошибки транспорта;
ответ, evidence и конечный URL согласованы; хост в scope; файлы действительно сохранены.
Последнее проверяет хранилище/граница handoff, не одна декларация в JSON.
`can_enter_step1` **не является** разрешением robots и не доказывает описание бизнеса.
У `Step1Input.crawl_permission` единственное начальное значение **unknown**.

Приоритет: INPUT/TARGET/OUTPUT -> failed; внешний переход -> needs_input;
окончательная сеть/HTTP -> failed; полученный непригодный 2xx -> partial/false;
пригодный HTML -> ok либо partial/true. Ошибка HTTPS, после которой реально получен
HTTP HTML, остаётся историей, а не блокирующей ошибкой выбранного ответа.
Подозрение на барьер не становится подтверждением без оснований классификатора.
Выбор другого URL после непригодного содержимого предлагается next_action; текущая
наблюдаемая запись остаётся partial/false, а не переименовывается задним числом.

## Транспорт, HTTP и содержимое

Транспортная ошибка: код `DNS_*`, `NETWORK_*` или ошибка TLS; HTTP-ответа может не быть.
При обрыве чтения статус/заголовки уже могут существовать, но body_complete=false.
HTTP-ошибка: транспорт получил, например, 403; это status_code и ErrorDetail категории http,
а не TLS failure. Непригодное содержимое: например, 200 с PDF или CAPTCHA; это content/access
причина, status_code остаётся 200. Ошибка сохранения имеет отдельную категорию output.

`tls_state`: not_observed, not_applicable (только HTTP), verified,
certificate_error, handshake_error. Ответ HTTPS допустим только с verified.
Таймаут не доказывает отсутствие HTTPS. HTTP fallback не исправляет TLS-наблюдение.

`ErrorDetail`: `{code, category, message, retryable, attempt_id}`; все поля обязательны,
attempt_id nullable. Коды - закрытый Literal, полный перечень в схеме ErrorDetail.
`errors` содержит объяснения, `reason_codes` - уникальные коды в порядке появления.
Сообщения безопасны для консоли, traceback и repr сетевых исключений туда не попадают.
Неожиданные программные ошибки будущая оркестрация не должна превращать в «сайт недоступен».
Отказ недоступной реализации - исключение `GeoAuditError`, не результат аудита failed.

## URL, область и сетевой адаптер

Правила IDNA закреплены: `idna==3.11`, UTS46, non-transitional, STD3; ASCII-хост в сети,
Unicode-хост для отображения. Сохраняются регистр пути, query и повторы параметров;
fragment удаляется. Неоднозначные dot-segments отвергаются, а не незаметно схлопываются.
Credentials, управляющие символы, backslash, неверные percent-escape и альтернативные
числовые IPv4 отвергаются. Нормализация не делает DNS-запросов и не означает разрешение порта.

Будущий транспорт обязан проверять все DNS IPv4/IPv6-ответы, отклонять mixed public/private,
private, loopback, link-local, reserved, metadata и mapped internal IPv6. Все новые назначения
проверяются снова. Разрешённый хост не снимает сетевой запрет.
Проверенные IP должны связываться с фактическим соединением, сохраняя исходные Host и SNI
и проверку TLS. У `HTTPX.AsyncClient` нет достаточной гарантии этой связи через один
DNS precheck. До реализации pinning/контролируемого egress живой клиент не предоставляется.

Требуемые настройки будущего клиента: TLS verify=True, trust_env=False,
proxy disabled, cookie persistence disabled, follow_redirects=False,
transport retries=0, явные UA/Accept-Language и таймауты из конфигурации.
HTTP2, авторизация, произвольные proxy и cookies текущей основе не нужны.
Разрешение нестандартного порта задаётся явно; HTTP80/HTTPS443 - начальное правило.

Ручной redirect: Location -> нормализация -> scheme/port/target -> visited/hops -> scope.
www-алиас требует наблюдаемого перехода, точной пары host/www.host и одинакового
registrable domain по локальному PSL с private-секцией; стороны не могут быть суффиксом.
Ни canonical, ни meta refresh, ни ссылка не расширяют scope.
PSL-снимок и его механизм ещё не выбраны, поэтому автоматическое распознавание алиасов
не объявляется работающим. Поле хэша в схеме само не доказывает проверку PSL.

Политика fallback: только подходящий окончательный транспортный сбой исходного HTTPS,
ровно один HTTP-кандидат с теми же хостом/путём/query, после допустимых повторов.
Certificate failure не повторяется перед fallback. NXDOMAIN, временный DNS, HTTP-статус,
барьер, внешняя цель, запрет назначения, исчерпание бюджета не запускают fallback.
Возврат HTTP к ранее неисправному HTTPS завершает FALLBACK_NO_USABLE_RESULT.
Проверка этой последовательности, retry jitter, Retry-After и лимита 1 старт/хост/сек
ещё относится к будущему исполнителю.

## Хранение и передача

Будущий каталог запуска: `output/runs/<run_id>/`; путь не выводится из URL.
`raw/` содержит файлы с непрозрачными именами. Manifest - EvidenceRecord с SHA-256,
размером, представлением и полнотой каждого файла. Представления различаются явно:
content_encoded, entity_bytes, decoded_text, attempt_observation.
Это тело HTTP-ответа, не wire/TLS capture. При TLS failure сохраняется наблюдение без тела.
Производное представление не перезаписывает исходное.

`EvidenceStore.publish` проверяет существование/размер/хэш всех доказательств,
публикует manifest, затем site.json через временный файл, fsync и os.replace.
Это атомарная замена одного JSON, не транзакция всего каталога и не гарантия сохранности
при отказе носителя. Каталог локальный, контролируемый приложением; защита от параллельной
враждебной подмены symlink/junction между проверкой и открытием не заявляется.
Отдельный run_id на повторный запуск и проверка записи до сети обеспечиваются будущим runner.
Если невозможно сохранить даже failed site.json, ошибка output должна остаться в API/CLI.

Диагностические заголовки - allowlist `Header.name`, повторы сохраняются tuple-списком;
Set-Cookie/Authorization туда не допускаются. `redacted` и `redacted_headers` фиксируют обработку;
Location может содержать секретный query, поэтому консоль не выводит его произвольно.
Хранилище сейчас получает уже подготовленные байты; потоковая запись и ограниченная
декомпрессия должны быть реализованы совместно с сетевым адаптером.

`Step1Input` включает исходный site, точный выбранный FetchAttempt и EvidenceRecord,
неизменённый BudgetSnapshot и crawl_permission=unknown. Дублирование небольшой метаинформации
намеренно: сериализованный объект самодостаточен и проверяет равенство исходной записи.
Путь файла относителен каталогу запуска, который явно передаётся потребителем.
`verify_step1_input` проверяет текущий UTC-дедлайн и физические доказательства без GET.
В одном процессе шаг 1 будет использовать тот же живой Budget. Межпроцессное возобновление
бюджета не реализовано: нужен консервативный пересчёт остатка с учётом времени простоя,
а не новый бюджет на 300 секунд. Сериализованный snapshot хранит достаточные исходные поля.

## Проверка и ограничения

Модели - источник истины для схем Draft 2020-12. JSON Schema проверяет форму и простые
ограничения; произвольные Python model_validator не становятся автоматически JSON Schema.
Для допуска к этапу нужны и схема, и Python-инварианты, и проверка файлов/актуального времени.
Схемы имеют стабильные URN `$id`, не требуют удалённого schema registry.

Тесты выполняются без интернета: примеры всех состояний; отрицательные инварианты;
URL/IDN; IP-контракт; fallback-таблица; бюджет; повреждённые/отсутствующие файлы;
atomic-write failure; handoff; CLI и явный отказ незавершённого runner.
Проверка IP-модели не заменяет интеграционные испытания настоящего pinning и DNS rebinding.
Статус реализации каждой строки алгоритма указан в `STEP_0_REQUIREMENTS.md`.

Зависимости выбраны по совместимости с Python 3.12, без требования использовать новейшие
версии: HTTPX 0.28.1, Pydantic 2.12.3, IDNA 3.11, tzdata 2025.2 (IANA-зоны на Windows).
Прямые версии заданы точно, транзитивные и хэши - в `uv.lock`; backend hatchling 1.27.0.
Среда проверена на Python 3.12.10/Windows. Совместимость будущих версий Python не объявляется
протестированной только потому, что метаданные разрешают >=3.12.

Технические основания: [HTTPX transports](https://www.python-httpx.org/advanced/transports/),
[Pydantic JSON Schema](https://docs.pydantic.dev/latest/concepts/json_schema/),
[uv locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/).
Сверены 31.10.2026; сетевые правила GEO являются решениями проекта.
